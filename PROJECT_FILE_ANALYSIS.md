## Major Findings

1. The active app works from the outer `hearly-extension` workspace.

   The root workspace only targets `hearly-extension`. The nested extension is not part of the workspace and should be treated as stale or experimental unless intentionally revived.

2. There is heavy duplication.

   Most files under `hearly-extension/hearly-extension/src` are byte-identical to files under `hearly-extension/src`. A few files differ, especially background/audio/content/enrollment pieces and ONNX model adapters.

3. Generated/vendor files are present in the project folder.

   `node_modules` and `dist` are present under the project tree. If this folder is intended for GitHub or handoff, these should usually be removed from version control and covered by `.gitignore`.

4. The outer app's cloud transcription only works when `VITE_HEARLY_API_BASE_URL` is set.

   Without that env var, `transcribeAudioInCloud` returns `null`. Background code handles that safely by doing nothing, so transcript UI may appear enabled while no transcription entries arrive.

5. The server voice endpoints are placeholders.

   `/api/voice/enroll` echoes the local embedding with a fake profile id. `/api/voice/verify` returns 501. This is fine for MVP scaffolding, but not production voice verification.

6. Sensitive data encryption is local-obfuscation, not strong at-rest security.

   `cryptoStorage.ts` encrypts values with AES-GCM, but stores the extractable AES key in the same Chrome local storage. It protects against casual inspection but not against an attacker or extension compromise with storage access.

7. Audio/content code has repeated platform logic.

   Meet, Zoom, and Teams content scripts repeat banner injection, mic bridge, tab capture, transcription toggling, and cleanup logic. This increases drift risk.

8. Some text encoding is corrupted.

   `README.md` and several comments/strings show mojibake or NUL-looking output. This should be normalized to UTF-8.

## Runtime Architecture

1. Popup UI stores enrollment, filter, transcript, and settings state with Zustand.
2. Popup toggles send messages to the background service worker.
3. Background requests `chrome.tabCapture.getMediaStreamId` and forwards stream ids to the active meeting content script.
4. Content scripts capture tab audio and optionally create overlapping audio chunks for transcription.
5. Injected page script patches `navigator.mediaDevices.getUserMedia` to process the user's microphone stream in the page context.
6. AudioWorklet compares a handcrafted 192-dimensional voice fingerprint against the enrolled embedding and ducks non-matching speech.
7. Cloud proxy server optionally forwards chunks to OpenAI transcription and chat completions.
8. Transcript entries are encrypted into Chrome local storage and shown in history/UI.
